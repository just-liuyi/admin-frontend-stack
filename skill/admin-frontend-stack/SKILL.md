# 后台管理前端技术栈规范

核心思路：**用约束换稳定性**。技术选型越明确，模型自由发挥的空间越小，产出就越一致、越好维护。
四条原则：优先复用成熟库；组件源码在仓库内可控；统一设计语言；同类功能只允许一个库。

## 先判断模式

| 模式 | 什么时候 | 做法 |
|---|---|---|
| 原型模式 | 用户只想看视觉效果、验证想法，或没有项目目录 | 交付单文件 HTML（可发布为页面）；不搭工程、不装依赖；仍遵守设计语言、图标、深浅色、响应式和四种状态 |
| 工程模式 | 已有项目，或用户要正式开发、长期维护 | 走下面的完整工作流 |

- 判断不了时，用一句话问用户；无法提问时按原型模式做，并在回复里说明"这是原型，不是正式工程"，问是否需要转成工程。
- 原型也要为迁移留路：颜色用 CSS 变量（命名与 `design-tokens.md` 的语义名对应），图标用 Lucide 官方图标的 SVG，布局和状态套用 `admin-layouts.md` 的原型，导航外壳遵守下方「导航外壳」的硬性规则。这样日后转成 React + shadcn，只是换写法，不用重新设计。
- 原型模式下，初始化脚手架、安装依赖、`check_deps.mjs`、`tsc` 都不适用；交付说明里要写明"未经工程检查"。

## 工程模式工作流（按顺序执行）

### 1. 先勘察，再动手
读取 `package.json`、`components.json`（如有）、`src` 目录结构，回答三个问题：
- 是新项目还是已有项目？
- 每个类别（图标、动画、状态、表单……）已经在用什么库？
- 已有哪些 `components/ui/*` 组件？

**优先级：项目已有依赖 > 本 skill 清单 > 清单外（需说明理由）。**
这样排序是因为已有项目的一致性比"我更喜欢的库"重要；并存两套同类库会让包体积、风格、心智负担一起变差。

### 2. 新项目初始化
**新项目直接按 `references/quickstart.md` 一步步做**（目标效果图在 `assets/previews/`）：建项目、装依赖、复制 `assets/` 里的外壳 / 页签 / 登录代码，得到能运行的后台骨架（已在全新空项目里实测）。之后再按需添加各页面的依赖。
默认 Vite + React + TypeScript；需要 SSR/SEO 或用户指定时用 Next.js（quickstart 只验证了 Vite）。
shadcn 初始化与风格选择见 `references/stack.md` 的「初始化」一节。
**默认风格 `radix-nova`**（紧凑，适合后台）；表格极度密集的页面可改用 Mira。
新项目同时配置好 ESLint 规则（见 `references/eslint-rules.md`），把「禁止混用」落成编辑器里的报错；注意锁定 TypeScript 6。

### 3. 选库
- 清单见 `references/stack.md`（按类别列出推荐库、用途、禁止混用的替代品）。
- 清单没覆盖的需求：先看 shadcn 官方组件是否已有（Sidebar、Data Table、Chart、Command、Sonner、Field 等），再看已有依赖能否满足，最后才引入新库，并在回复里用一句话说明为什么。
- **按复杂度决定要不要用库。** 交互复杂的功能不手写，用成熟库：拖拽、可调整面板、表格的排序/筛选/分页/列管理、表单校验、Toast、日期选择。简单场景不必为了"符合清单"硬上库：几行只读数据的静态表格直接用 shadcn Table 或原生表格；两三个字段的表单用受控组件即可。判断标准是"手写这个会不会很快变成在重造轮子"。
- **按需引入依赖。** 清单里的库是"需要这项能力时用什么"，不是"默认全装"。先列出这个项目需要哪些能力，只安装对应依赖（能力与依赖的对照见 `references/stack.md`），之后新增功能时再补。

### 4. 写代码前确认 API 版本
这些库迭代很快，凭记忆写容易用到过时 API（典型：react-resizable-panels v4 改名、dnd-kit 新旧两套包、TanStack Table v8/v9 不兼容）。**先读 `package.json` 确认每个库的主版本，再决定用哪套写法。**
- 先读 `references/patterns.md`，里面是核实过的用法与坑。
- 其中没有的、或与项目已装版本不一致的，查 `node_modules/<pkg>/` 的类型定义或官方文档再写。
- 项目里已经在用旧 API 时，沿用旧 API，不要在同一个项目里混用新旧两套。

### 5. 按页面原型搭界面
后台页面高度同质化，直接套 `references/admin-layouts.md` 里的原型：应用外壳、列表页、表单页、详情页、仪表盘、登录页。
每个数据页面必须覆盖四种状态：加载（Skeleton）、空、错误、无权限。

**导航外壳（侧边栏 + 顶栏）先读 `references/navigation.md`，并直接复制 `assets/navigation/` 里验证过的代码**，不要从零写。硬性规则（原型模式同样适用）：
- 收放按钮在**侧边栏顶部**，与 Logo 同一行（折叠后在 Logo 正下方）；不放侧边栏底部，不做成菜单项。手机端顶栏左侧另加一个只在手机显示的打开按钮。
- 折叠用 `collapsible="icon"`，只剩图标，悬停显示名称；折叠状态只由 `SidebarProvider` 管理（cookie），不再存 Zustand。
- 菜单最多两级：父级只展开不跳转，子项无图标、带竖向引导线；折叠时点父级图标向右弹出子菜单浮层。选中状态由当前路由决定，用主色浅底，子页面所在的父级自动展开。
- 层次靠两种线：侧边栏顶部区域与顶栏同高（`h-14`），底线连成一条；分组之间用 `SidebarSeparator` 分隔。不给每个菜单项加横线，也不把分组装进卡片。
- 个人入口在**顶栏最右**：头像 + 下拉菜单（姓名邮箱、个人设置、切换主题、退出登录）。侧边栏底部不放用户菜单。
- 头像用自动生成的 SVG：无名字显示人形剪影，有名字显示首字母，多人并列时按姓名配色；有图片时显示图片，加载失败回落到 SVG。
- **多页签默认开启**（是标准功能，不用等用户提）：读 `references/tabs.md` 并复制 `assets/tabs/`。首页固定不可关；右键页签和右侧 ⌄ 按钮都提供 刷新 / 关闭 / 关闭左侧 / 关闭右侧 / 关闭其他 / 关闭全部；最多 10 个，超出时关掉最左边的可关闭页签；切换页签保留页面状态（React 19.2+ 的 `<Activity>`，不引入第三方 keep-alive 库）；只在电脑上显示。只有用户明确说不要页签时才改用单页面外壳。

**登录页先读 `references/login.md`，并直接复制 `assets/login/`**（含登录守卫与回跳）。硬性规则（原型模式同样适用）：
- 电脑上左右分栏：左边主色浅渐变底 + Logo + 四个会互动的几何小人（跟随鼠标；输入密码时偷看；显示密码时回避；登录失败时摇头）；右边"欢迎回来" + 账号密码 / 手机验证码两种登录方式。手机上不显示小人，只显示居中卡片。
- 小人颜色每次打开页面随机分配，深色身体上的五官用白色；系统开启"减少动态效果"时不动。
- 切换登录方式时整块不上下跳（两个表单叠放在同一格）；点击页签不出现灰色焦点框（焦点框只在键盘操作时显示，全站 Tabs 通用改法见 `patterns.md`）。
- 未登录访问任何页面跳登录页并带回跳地址；回跳地址只接受站内路径；登录后的跳转只在 `App.tsx` 做一次；主题在应用最外层应用，登录页也支持深色。
### 6. 图标与图形
图标统一 Lucide；大位置用实心色块 + 白线，小位置用浅色底 + 彩线，按钮菜单里不加色块。
色块组件、自绘图标、品牌图标（Lucide v1 已删除，改用 Simple Icons）、SVG 处理、空状态插画、Logo 的规则见 `references/icons-and-graphics.md`。
自绘的图标或插画必须先让用户看到效果、确认后再入库。

### 7. 遵守设计语言
颜色、圆角、间距、字体的规则见 `references/design-tokens.md`。
要点：只用语义 token（`bg-background`、`text-muted-foreground`、`border`），不写死十六进制色值和任意像素值；这样深浅色模式和风格切换才会自动生效。

### 8. 交付前检查
按下面的顺序做。**能做的都做；做不到的，在交付说明里写明"未验证"，不要假装做过。**
1. **静态检查**：`tsc --noEmit` 和 ESLint（有哪个跑哪个）。`tsc` 能抓到已删除的 Lucide 品牌图标导入；ESLint 规则（`references/eslint-rules.md`）能拦住重复库、废弃库和拼接类名。已有项目若还没有这些规则，把它们合并进现有 ESLint 配置，不要新建第二份；历史遗留目录用 `warn` 降级，不要为了通过检查整体关掉规则。
2. **构建**：build 能通过。
3. **依赖体检（可选）**：接手已有项目，或想看依赖级的重复与版本提醒时，运行 `node scripts/check_deps.mjs <项目根目录>`。只依赖 Node.js 18+ 自带模块，不需要 `npm install`。输出分三级：
   - **错误**（编译报错或静默失效）：必须先修。
   - **警告**（同类依赖重复、已废弃库、新旧包混用）：需要人判断。已有项目里常是历史遗留，**不要顺手重构**，只在交付说明里提一句。
   - **提示**：版本提醒，参考即可。
   新项目加 `--strict`，警告也算失败。已有项目若想让历史遗留不再反复报警，可运行 `--write-baseline` 登记到 `.stackcheck.json`，但这会改变检查结果，**必须先征得用户同意**，不要自行登记来让检查通过。个别源码行确需例外时，行尾加注释 `stack-check-ignore`，并在说明里写明原因。
   Node 不可用时可以跳过脚本，但要在交付说明里写明"未做依赖体检"。
4. **行为**：关键交互、空/错误/无权限状态是否真的走过一遍。有测试就跑；没有就说明手动走查了什么。
5. **视觉**：桌面宽度、手机宽度、深色模式。无法渲染或截图时，写明"未做视觉验证"。
6. 把下方反模式过一遍。

交付说明必须包含：沿用了什么、新增了哪些依赖及原因、真正执行过哪些验证、未验证事项、已知限制。
**除非确实执行并看到了结果，否则不要说"测试通过""已验证"。**

## 反模式（出现即修正）

- 同时存在 `lucide-react` 和 `react-icons` / `@heroicons`；同时存在 `motion` 和 `framer-motion`
- 复杂表格（需要排序、筛选、分页或列管理）手写 `<table>` 逻辑，而不是 TanStack Table + shadcn Table（简单静态表格不在此列）
- 把接口数据放进 Zustand（服务端数据归 TanStack Query；Zustand 只放客户端 UI 状态）
- 写死颜色 `#3b82f6`、`bg-blue-500` 表达品牌/状态色，而不是语义 token
- 复制粘贴一个 shadcn 组件的内部实现到业务页面，而不是 `shadcn add` 后在 `components/ui` 里改
- 删除类操作没有 AlertDialog 二次确认
- 用 `alert()` / `confirm()` / 自制弹层代替 Dialog、AlertDialog、Sonner
- 在循环里 `await` 逐个请求、在 `useEffect` 里手写数据请求（用 TanStack Query）
- 给每个按钮、卡片都加动画（后台以效率为先，动画只用于过渡和反馈）
- `import { Github } from "lucide-react"`（Lucide v1 已删除品牌图标，会编译报错）
- 给每个功能分配不同颜色的图标色块（默认主色，只有状态语义才换色）
- 手写 `bg-${tone}` 这类拼接类名（Tailwind 不识别；ESLint 规则会拦）
- 自绘品牌图标，或自绘图标未经用户确认就入库
- 收放按钮放在侧边栏底部、做成一个菜单项，或折叠后找不到；手机端没有打开菜单的入口
- 用户菜单放在侧边栏底部，或侧边栏和顶栏各放一个；头像用外链图片或空白圆圈，没有生成的 SVG 回退
- 侧边栏折叠状态同时存在 `SidebarProvider` 和 Zustand/localStorage 两处
- 三级及以上菜单；父级菜单既能展开又能跳转
- 用户没说不要，却没有页签栏；页签栏缺少关闭左侧/右侧/其他/全部，或首页能被关掉；用第三方 keep-alive 库代替 `<Activity>`
- 因为"在默认栈里"就安装用不到的依赖
- 没有真正执行就声称测试通过、已验证

## 例外规则
用户明确点名了某个库或风格时，以用户为准，但要指出与清单的冲突和后果（如"你指定的 X 与已有的 Y 功能重叠"），让用户决定是否替换，而不是默默两套并存。
